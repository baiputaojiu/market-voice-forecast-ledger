# 重要な決定と理由

## 記録規則（Recording Rules）

- IDは変更しない。
- 状態は「採用」「置換済み」「却下」のいずれかとする。
- 現在の要件は `requirements.md` を正本とし、このファイルには判断理由と重要な比較案を残す。
- 小さな実装詳細や日々の進捗は記録しない。

## 採用中の決定（Accepted Decisions）

### DEC-001: ローカルWebアプリ

- 状態: 採用
- 決定: React＋TypeScript＋Vite、FastAPI、SQLite、Windowsバックグラウンドワーカーを採用し、`127.0.0.1` だけへ公開する。MVPではローカルトークン、`Origin`検査、Windowsアカウント認証を追加しない。
- 理由: デスクトップ向けの密度ある比較UI、長時間バックグラウンド処理、ローカルデータ保護を両立できる。
- 影響: 信頼できる単独利用PCを前提とする。同一PC上の別プロセスやブラウザからの到達を防ぐ認証境界ではないため、このリスクを画面・運用資料に明記し、追加防御は将来機能とする。
- 比較案: ネイティブデスクトップアプリ、クラウドWebアプリ。
- 却下理由: ネイティブUIは初期開発コストが高く、クラウドは音声・全文文字起こしの公開境界と運用費が増える。

### DEC-002: 予想分析はCodex CLI

- 状態: 採用
- 決定: OpenAI APIをアプリへ直接組み込まず、構造化出力付き `codex exec` を使う。
- 理由: ユーザーのCodex認証と最上位モデルを利用し、APIキー管理を増やさない。
- 影響: アプリはCodex CLIの存在とログイン状態を検査し、モデル利用不能時は停止する。

### DEC-003: 最上位モデルを固定

- 状態: 採用
- 決定: `gpt-5.6-sol` とreasoning effort `max` を明示し、下位モデルへ自動フォールバックしない。
- 理由: 分析品質を最優先し、モデル差による分析結果の不透明な変化を防ぐ。

### DEC-004: 分析根拠を保存済み発言に限定

- 状態: 採用

- 理由: 「誰がいつ何を予想したか」を監査可能にし、外部知識が混ざった独自予想へ変質することを防ぐ。ユーザー実施のスモールテストでは外部ツール呼び出し0件を確認できた。

- 理由: 話者割当の修正履歴と予想分析の再現性を保ち、低信頼話者を分析から除外できる。

### DEC-013: 期間を絶対日付範囲へ正規化

- 状態: 採用
- 決定: 週は月～日、月は暦月とし、「何月第1週」はその月の1日を含む月～日とする。相対表現をYouTube公開日のJSTから絶対範囲へ変換し、採用対象発言で明示された年月日・期間は明示期間として区別する。曖昧表現は時期不明とする。
- 理由: 収録日は通常公開されず、防御可能な共通基準にできない。公開日なら別PC・再分析でも同じ期間を再現でき、Codexによる収録日の推測を防げる。
- 影響: 収録から公開まで間がある動画では本人の意図した相対期間とずれる可能性があるため、公開日基準であることを画面に明示し、手動修正は監査する。

### DEC-014: 相反見解を平均しない

- 状態: 採用
- 決定: 同じ分析主体・資産・比較可能な対象期間・条件レイヤーに属する採用可能な予想を、UTC正規化済みのYouTube公開日時ごとにまとめる。`+1`・`+2`の上昇系と`-1`・`-2`の下降系が同じ公開日時にあれば、動画、直接性、対象解決、期間具体性にかかわらず、両方向を持つ見解相違とする。最新公開日時群の上昇系・下降系が、いずれかの古い公開日時群と逆なら見解変更とし、途中の同方向再投稿では変更履歴を消さない。最新群を現在見解、古い群を履歴・反証として残す。同じ公開日時群に逆方向がない場合だけ、直接予想、次に期間具体性を代表表示に使える。条件付き予想は無条件予想と競合させない。動画IDとstatement IDは決定的な順序付けにだけ使い、逆方向の選択には使わない。
- 理由: 上昇と下降を機械的に横ばいへすることは、発言の意味を失わせるため。
- 置換した案: 同じ公開日時では直接予想、次に期間具体性を使って片方を現在見解にする方式。同時に公表された逆方向を片方だけへ縮約せず、見解相違として保持するため置換した。

### DEC-023: 市場全般の表現を監査可能な推定割当へ変換する

- 理由: 本人が指数名を使わない市場見通しも比較対象へ反映しつつ、Codexが行った対象解決を本人の直接発言と誤認させないため。

### DEC-024: 転換点・判断不能・横ばい・空欄を混同しない

- 状態: 採用
- 決定: 底入れや天井打ちは独立した転換点とし、上昇または下降へ強制変換しない。判断不能、横ばい、関連発言なしの空欄も別状態として扱う。
- 理由: 発言が示す市場局面と、方向、分類不能、証拠なしは意味が異なり、単一の中立値へ畳むと監査性を失うため。

### DEC-025: 条件付き予想を独立レイヤーにする

- 状態: 採用
- 決定: 無条件予想と条件付き予想を別軸で保存し、ヒートマップでは条件付き印を付け、条件文を常に確認可能にする。
- 理由: 条件成立を確認していない予想を基本見解と同じ確度で表示しないため。

### DEC-026: 分析用の動画日時を公開日時だけにする

- 状態: 採用
- 決定: 分析用にはYouTube公開日時だけを保存する。収録日時は保存・推定せず、システム作成・取得日時は内部監査にだけ使い、分析へ使わない。
- 理由: 収録日時は通常公開されず、システム取得日時はユーザーの実行都合で変わる。公開日時だけが公開情報として一貫して取得でき、日付指定分析を再現できる。
- 置換した案: 収録日、公開日、取得日を別々に保存し、相対時期を収録日基準にする方式。利用できない収録日が通常状態となり、取得日は分析上の意味を持たないため置換した。

### DEC-027: 音声・全文文字起こしに保存期限と削除経路を設ける

- 状態: 採用
- 決定: 一時音声は処理完了後に削除する。自動削除は専用一時音声フォルダー内だけに限定し、範囲外パスを拒否する。全文文字起こしと正確なCodex入力本文は非公開内部データとし、作成日から365日を既定期限にする。30・90・180・365日・無期限の設定と手動削除を提供し、通常画面には必要最小限の根拠部分だけを表示する。
- 理由: 再現可能な分析に必要な内部証拠を保持しながら、権利・プライバシー・保存容量のリスクを抑えるため。

### DEC-028: 5～10分チェックポイントと実完了数の進捗を使う

- 状態: 採用
- 決定: 動画情報取得・チャンネル判定、音声取得、分割文字起こし、話者割当、主体別分析入力抽出、Codex分析、自動割当、ヒートマップ集計の順で処理し、5～10分相当の作業unitごとに再開可能なチェックポイントを保存する。中断中または再試行対象の失敗unitは `pending` へ戻してunit先頭から実行し、途中出力は採用しない。入力・成果物hashとモデル・設定・契約versionが一致する `success` unitだけを再利用する。全upstream unitと後段検証の完了後、最終反映unitが現在予想、run受理event、監査event、ヒートマップ、自身の `success`、jobの `succeeded` を原子的に更新する。動画情報取得と音声取得を別段階にし、進捗は各段階の実完了数から算出する。
- 理由: ユーザー実施のCPUスモールテストでは40分級動画の文字起こし約74分、話者割当約4分、Codex分析約4.5分を要し、長時間処理の中断回復と正確な進捗把握が必要になったため。

### DEC-029: 現在値と追記専用監査ログを組み合わせる

- 状態: 採用
- 決定: 話者割当と同一分析scopeの正規化結果は現在値を1件だけ保持し、修正時に変更前・変更後の構造化JSON、理由、操作者、日時を追記専用監査ログへ保存する。監査ログ、分析run、レビュー履歴はサービス層とSQLiteの両方で更新・削除を防ぐ。全文文字起こしや正確なCodex入力本文は監査JSONへ複製しない。
- 理由: 通常検索を単純にし、修正前後を監査可能にしながら、全文データの重複と削除期限の迂回を防ぐため。
- 影響: 話者修正では依存分析をstaleにし、再分析成功後だけ現在結果を更新する。異なる基準日時の分析scopeは別々に保持する。

### DEC-030: 指数割当信頼度をCodexとアプリ規則の両方で検査する

- 状態: 採用
- 決定: 信頼度を `high`、`medium`、`low`、`unresolved` で保存する。Codex自己評価とは別に、分析主体の採用対象発言内の直接言及、周辺の採用対象発言、競合市場をアプリ規則で検査し、異なる場合は低い側を自動採用上限にする。個人主体では聞き手だけに存在する手掛かりも検査する。
- 理由: Codexの自己評価だけで誤った対象指数を高信頼として表示せず、同じ入力へ決定的なゲートを適用するため。
- 影響: `low` と `unresolved` は主ヒートマップへ自動採用せず、ユーザーの承認・修正・却下と理由を監査する。4人すべてについて、聞き手発言だけを根拠に `high` または `medium` にしない。

### DEC-031: 基準日時ごとの分析scopeを共存させる

- 状態: 採用
- 決定: 分析主体と選択したJST暦日の組を一意なscopeとし、異なる基準日の結果を共存させる。内部の動画包含判定にはJST翌日0時を表すUTCの排他的上限を保存・使用する。同じscopeの再分析は、検証成功後だけ現在結果を置換し、変更前後を監査する。
- 理由: ユーザーが年月日を選んで当時利用可能だった発言だけの予想を比較しながら、同じ日付の修正版を通常画面で単純に参照できるようにするため。

### DEC-033: 動画と発言を重複排除しない

- 状態: 採用
- 決定: 元動画、切り抜き、Shorts、再投稿を重複判定・統合・除外せず、それぞれ独立した動画、発言、根拠として保存・分析・集計する。
- 理由: ユーザーが、後から公開された切り抜きが新しい発言として扱われる可能性と、同内容によって根拠数が増える可能性を許容し、出典単位の記録を優先した。
- 影響: 動画・発話のcanonical選択やduplicate groupを分析入力ゲートに使わない。公開日時の新しさによる現在見解選択は切り抜きにも通常どおり適用する。

### DEC-034: 時期不明を承認後に専用列へ表示する

- 状態: 採用
- 決定: 時期不明の将来予想は未承認の間は主ヒートマップへ入れず、ユーザー承認後は週表示・月表示に共通する「時期不明」専用列へ表示できる。承認・却下と理由を監査する。
- 理由: 根拠のない期間を創作せず、時期を特定できない予想の存在も比較画面から失わないため。

### DEC-035: 根拠を複数区間へ結び付け本文一致を検証する

- 状態: 採用
- 決定: 1つの分析済み発言へ複数の分析対象発話区間を順序付きで結び付ける。4人すべてについて同じperson主体へ本人割当された区間だけを許可する。各短い根拠は、対応する保存済み文字起こし本文の連続部分と一致する場合だけ採用する。
- 理由: 条件、対象、方向、時期が複数区間に分かれる発言を保持しながら、Codexの自由な要約を本人の原文根拠と誤表示しないため。

### DEC-036: M1を設計、M2を実装とする

- 状態: 採用
- 決定: M1は設計フェーズとし、修正済み設計と実装計画の承認で完了する。中核バックエンド実装はM2の最初のサブプロジェクトとする。
- 理由: 設計完成とコード実装の完了条件を混同せず、進捗と承認ゲートを明確にするため。

### DEC-037: M2実装計画を一つの小粒度計画にする

- 状態: 採用
- 決定: M2中核バックエンドの詳細実装計画は1ファイルに保ち、独立した失敗テスト、実装、検証、レビューが可能な16～20程度のタスクへ分割する。
- 理由: 全体の依存順序を一望できる状態を保ちながら、旧12タスク案の大きすぎる作業単位を解消するため。

### DEC-038: DB時刻はUTC、暦日規則は固定JSTにする

- 状態: 採用
- 決定: DBへ保存する日時と内部比較はUTCに統一し、画面表示、選択日の締切、相対期間、週・月境界は固定JST（UTC+9）で計算する。`ZoneInfo`、IANA timezone database、`tzdata`へ依存しない。選択日の包含判定はJST翌日0時をUTCへ変換した排他的上限を使う。
- 理由: UTC保存の一貫性を保ちながら、既に確定した「来週はJSTの月曜～日曜」という利用者向け意味を維持し、WindowsでIANA timezone databaseがない環境でも決定的に再現するため。
- 置換しない事項: DEC-013のJST週境界と公開日基準は維持する。UTCの週境界へ変更しない。

### DEC-039: rollbackは再接続後の永続状態まで検証する

- 状態: 採用
- 決定: 作業unitの成功確定前と現在結果の原子的置換中に故障を注入するテストは、同一connection内だけでなく、connectionを閉じて開き直した後の `pending` unit、旧current集合、旧heatmap、旧scope状態まで照合する。Python例外rollbackと別process強制終了・WAL回復は別試験として扱う。
- 理由: 同一connectionの見かけ上のrollbackだけでなく、再起動相当の読み直しでも部分反映されていないことを保証するため。

### DEC-040: 4人を設定差だけの個人DiscoveryProfileへcutoverする

- 状態: 採用
- 決定: 木野内栄治、大川智宏、江守哲、千竈 鉄平をすべてperson subjectとし、seed channelと明示検索語の設定差だけで同じorchestratorを通す。seedは発見起点であって収集・分析allowlistではない。旧organization/fixed-channel runtimeはreset-requiredな単一migrationで除去し、dual-read/dual-writeを設けない。
- 理由: seed外の本人出演を候補として保持しながら、収集時点の発見経路と、後続の本人出演・本人発言確認を混同しないため。主体別collectorとlegacy compatibility分岐を残すと、範囲規則と再実行が複線化する。
- 影響: DEC-006とDEC-032を置換する。千竈は暁投資顧問公式seed内の全話者ではなく、本人確認済み区間だけを後続分析へ渡す。既存pre-cutover DBは変更せず`COLLECTION_MODEL_RESET_REQUIRED`で停止し、利用者が手動退避後に空DBを再作成する。

### DEC-041: credentialと日次実行をWindowsの既存機構へ限定する

- 状態: 採用
- 決定: YouTube API keyはWindows Credential Managerだけに保存し、日次時刻はWindows Task Schedulerだけを正本とする。Taskは既定06:00 JST、`StartWhenAvailable=true`、multiple-instance `Queue`、ログオン中のinteractive tokenで同じ`youtube-sync worker --once`を起動する。
- 理由: secretをDB、設定file、環境変数、argvへ複製せず、長寿命serviceを追加しないで停止中・重複起動からdurable queueを回復するため。

### DEC-042: collectionは出演未確認candidateで停止する

- 状態: 採用
- 決定: seed/search/manualから正規metadata、append-only observation、人物別candidate、初期`presence_unverified`までだけを作る。collectionから音声、文字起こし、speaker assignment、confirmed/rejected decision、分析jobを自動生成しない。
- 理由: 発見と本人確認・分析の責務を一方向に保ち、再発見やretryが音声・分析loopを生成することを防ぐため。

### DEC-043: quotaをcall前に原子的に予約し最小検索windowを継続する

- 状態: 採用
- 決定: `search.list`の100 attempts/dayとread系3 endpoint合計10,000 attempts/dayをUTC日bucketでcall前に原子的に予約する。exact limitの次はproviderへ接続せず24時間deferする。複数日検索windowはpage 10で分割するが、分割不能な1日windowはdurable tokenでpage 11以降を継続し、完全消費前にはsource cursorを進めない。
- 理由: crash時の過少計上と並行実行による上限超過を防ぎつつ、結果密度の高い1日を恒久失敗やcursor欠落にしないため。
