## 目的

M2事前フィージビリティ検証の38シナリオは全件成功した。一方、Windowsのタイムゾーン依存、作業unitの中断回復、rollback後の永続状態確認、公開日時が同じ予想の競合規則について、M2本実装前に設計とテスト計画を明確にする必要がある。本書は、ユーザーが承認した修正だけを正本へ反映するための差分設計である。

## 採用する方式

### 1. UTC保存と固定JST暦

- DBへ保存する日時と内部の日時比較はUTCに統一する。
- 画面表示、選択日の締切、相対期間、週境界、月境界は固定JST（UTC+9）で計算する。
- 日本にはMVPで扱う期間に夏時間がないため、`ZoneInfo`、IANA timezone database、`tzdata`へ依存しない。
- Pythonでは固定offsetのtimezoneを共有定数として使い、OSのタイムゾーン設定に依存させない。
- 「今週」「来週」「再来週」は従来どおりJSTの月曜日から日曜日とする。UTC週へ変更しない。
- 選択日を含む動画の判定は、JST翌日0時をUTCへ変換した排他的上限 `published_at < cutoff_exclusive_utc` を使う。これは「選択日JST 23:59:59まで」を小数秒の取りこぼしなく表現する。
- 相対期間は、保存済みのUTC公開日時を固定JSTへ変換した暦日から計算する。

### 2. 5～10分の作業unit単位で再実行

- 長い工程全体ではなく、決定的manifestに含まれる5～10分相当の作業unitを回復単位にする。
- unitは `pending -> running -> success` を正常経路とする。出力の検証と `success` 確定は同一transactionで行う。
- 中断時に `running` のまま残ったunitと、再試行対象になった失敗unitは、再開処理で `pending` に戻し、そのunitを先頭から実行する。
- 途中出力は正式成果物として参照せず、再開時に再利用しない。失敗した試行、エラーコード、試行回数はeventまたは監査情報として残す。
- `success` unitは、入力hash、成果物hash、モデル・設定・契約versionがすべて一致する場合だけ再利用する。
- 8分割の文字起こしで1～4が成功し5が中断した場合、1～4を再利用して5だけを最初から実行する。
- 最終反映unit以外の全upstream unitと後段検証が完了するまで、現在予想とヒートマップへ途中結果を反映しない。最終反映unitは、現在予想、run受理event、監査event、ヒートマップcache、最終unitの `success`、jobの `succeeded` を一つのtransactionで確定する。このtransactionが失敗した場合、最終unitは回復時に `pending` へ戻り、旧表示集合を維持する。

### 3. 公開日時群による見解相違と見解変更

競合を比較する意味単位は、`分析主体 × 資産 × 条件レイヤー × 比較可能な対象期間` とする。条件付きと無条件、または比較できない対象期間は混ぜない。

- 主ヒートマップへ採用可能な候補を、UTC正規化済みのYouTube公開日時で群にする。
- 上昇系は `+1`・`+2`、下降系は `-1`・`-2` とする。同じ公開日時群に上昇系と下降系が存在する場合は、同一動画か別動画か、直接予想か発言内推論か、直接言及か推定割当か、期間具体性が同じかにかかわらず `disagreement` とする。
- `disagreement` は両方向とすべての独立した根拠を保持し、横ばいへ平均しない。
- 最新公開日時群の方向が、いずれかの古い公開日時群と上昇系・下降系で逆なら `changed` とする。途中に同方向の再投稿があっても変更履歴を消さない。最新群を現在見解とし、古い群は変更履歴・反証として保持する。
- 上昇系と下降系だけを明確な逆方向とする。横ばい、転換点、判断不能、空欄は従来どおり独立状態であり、自動的な見解相違・見解変更へ変換しない。
- 同じ方向の動画、切り抜き、Shorts、再投稿は統合・重複排除せず、独立根拠として数える。
- `low` と `unresolved`、未承認の時期不明、その他ヒートマップ不採用候補は、保存しても主表示の競合判定へ入れない。レビュー後に採用可能になれば再投影する。
- 動画IDとstatement IDは決定的な表示順・serializationにだけ使い、同じ公開日時の相反方向から一方を選ぶ意味上の優先順位には使わない。
- 同じ公開日時群に上昇系・下降系の対立がない場合は、従来の直接予想、次に期間具体性という順位を代表表示の選択にだけ使える。全独立根拠は保持し、この順位で根拠を削除しない。

### 4. ヒートマップslotへの投影

- 正規化された元の予想期間は変更せずに保持する。
- 週・月cellは、その表示期間と交差する採用可能な予想を集めて投影する。
- 同じ表示slotへ複数期間が重なる場合も、公開日時群の規則を適用する。
- 条件レイヤーは分離したままにし、無条件予想との見解相違・見解変更を作らない。
- 時期不明は承認後も専用列だけへ表示し、通常の週・月slotへ推測割当しない。

### 5. rollbackと再接続による確認

- 作業unitの出力保存後・`success`確定前に故障を注入し、connectionを閉じて開き直した後もそのunitが成功扱いされないことを確認する。
- 現在結果の置換中に故障を注入し、connectionを閉じて開き直した後も旧current集合、旧heatmap、旧scope状態が残ることを確認する。
- 同一connection内の確認だけで完了としない。
- Python例外によるrollback試験と、別process強制終了・WAL回復試験は区別する。後者はM2の追加統合試験として扱う。

## M2計画への変更

- Task 1: 固定UTC+9 helper、JST翌日0時の排他的cutoff、Windows境界試験を追加する。
- Task 6: staleな`running`と再試行対象unitの`pending`復帰、unit先頭からの再実行、途中成果物不採用、再接続後の状態確認を追加する。
- Task 7: 分析runと決定的なjob-attempt履歴を結び、manifest先頭の入力固定unitと末尾の最終反映unitを各1件だけ要求する。主体、cutoff、policy/assignment、入力本文hash、設定versionから入力契約hashを再計算し、別入力用jobの誤接続を拒否する。停止後の後継jobは、run所有の成功済み成果物を同一hashで全件再利用できる場合だけ同じrunへ追記する。
- Task 8～13: 各Codex batch、発言正規化、期間正規化、指数割当、予想投影の永続出力と対応unitの `success` を同じtransactionで確定し、実際の成果物と進捗を分離しない。
- Task 10: `ZoneInfo`例を固定JST helperへ置換し、UTC/JSTの日付・週境界試験を追加する。
- Task 13: 同じ公開日時の逆方向を無条件に見解相違とし、異なる公開日時の反転を見解変更にする専用試験を追加する。
- Task 14: 故障後にconnectionを閉じて再接続し、旧current集合が残る試験とupstream unit gateを追加する。現在行置換はcaller-owned transaction内の非公開primitiveに限定し、後続Task 16へ依存させない。
- Task 16: 複数期間と条件レイヤーが同じ表示slotへ重なる試験、多対多の元予想link、現在結果・heatmap・最終unit・jobの原子的な最終反映を追加する。完了runと現在runのreviewに対する公開更新経路をここで初めて設け、現在行だけを置換する迂回経路を作らない。
- Task 19: 合成E2Eに加え、Windows子processを最終反映transaction内で強制終了し、再起動後のSQLite/WAL状態を確認する。電源断保証とは区別する。

## 受け入れ条件

1. Windowsで`ZoneInfo`と`tzdata`なしにUTC保存、JST表示、JST週境界、選択日cutoffを再現できる。
2. UTCでは前日でもJSTでは翌日になる公開日時から、「来週」を正しいJST月曜～日曜へ変換できる。
3. 8 unit中1～4成功、5中断の永続状態から、再接続後に5だけを最初から実行できる。
4. 途中成果物だけが存在してもunitを成功扱いせず、主ヒートマップを更新しない。
5. 全upstream unit完了後の最終反映transactionに失敗した場合、再接続後も旧集合が完全に残り、最終反映unitだけが再実行対象になる。
6. 同じ公開日時・同じ比較単位の上昇と下降は、直接性や期間具体性に関係なく見解相違になる。
7. 異なる公開日時の上昇・下降反転は見解変更になり、最新群と履歴をともに参照できる。
8. 異なる条件レイヤーまたは比較不能な対象期間は競合しない。
9. `low`・`unresolved`は承認前に競合判定と主ヒートマップへ入らない。
10. 現在行だけを変更してheatmap、run受理event、最終unit・job状態を迂回する公開更新経路がない。
